# FT3 production development infrastructure design

Status: proposed; planning only. User approval of implementation and every upstream action remains separate. Scope is Stripe FT3 V1 in this repository, including support for the prepared UUID candidate, not the separate V2 ecosystem.

## Purpose and choices

Provide a fresh-checkout workflow that catches catalog regressions, preserves consumer interfaces and stored identities, gives maintainers precise change reports, and can reproduce every claimed validation result. Production quality means explicit contracts, safe failures, portable tests, maintainable Python, and evidence bound to exact inputs; passing tests do not prove fraud-content correctness.

Recommended: a small Python package sharing parsing, validation, reporting and export primitives, with standard-library runtime and unittest tests. Hardened reuse of the prototype without decomposition would preserve its coupled Git/history assumptions. A database/API/full STIX or MISP exporter would add scope without solving the identified development risks. The prototype is reference material, not production code to copy wholesale.

## Scope and boundaries

- Build strict snapshot audit, trusted change comparison, pure deterministic CSV projection, field-level change reporting, portable test fixtures, CI configuration, and contributor instructions.
- Preserve all production catalog bytes during infrastructure implementation. Fixes to the actual taxonomy, tactic domains, dates, UUID adoption, and CSV formatting are separately reviewed changes.
- Public IDs and existing UUIDs cannot be removed, renumbered, reassigned or regenerated. Additions are supported; counts of 137 techniques/12 tactics are snapshot evidence, not permanent size limits.
- Generic code migrations, retirements, merges/splits, and adoption of external UUID versions are explicitly unsupported in this cut. Reject them with actionable diagnostics; they need a separate approved migration design. In particular, arbitrary transition triples cannot authorize identity changes.
- Do not create/update/close PRs or issues, push branches, change repository settings, or contact maintainers during planning or local implementation. User approval must precede upstream actions.

## Data contracts

Versioned declarative contract files describe the exact existing 22 technique fields and 9 tactic fields, their order and string types, required nonblank fields, ID grammars, date grammar and relationships. UUID profile adds one final technique column and requires a canonical RFC UUIDv4 for every new first-party assignment. Legacy profile has no UUID field. Candidate input cannot select a weaker profile; comparison takes it from trusted policy. A bootstrap-approved policy can explicitly allow the legacy-to-UUID transition against the exact previously reviewed assignment registry. Contracts live in ft3_tools/resources/contracts and are included as package resources; installed filesystem commands load them with importlib.resources, independently of cwd. Git comparison loads the same paths from accepted base blobs.

All unknown fields are rejected pending a reviewed contract change. Optional existing fields retain empty strings. No trimming, coercion, Unicode normalization, inferred list delimiters or undocumented enum constraints. Technique ID grammar is FT followed by exactly three digits, optionally a dot and exactly three digits; tactic ID is FTA followed by exactly three digits. Tactic ID key remains uppercase ID. Empty/duplicate tactic names are invalid because names are references.

Dates retain their existing representation: techniques M/D/YY with no leading zeros; tactics MM/DD/YYYY. Technique two-digit years explicitly mean 2000–2099; no library pivot is inherited. This finite interpretation requires documented owner acceptance as a policy proposal, preserves every current date, and does not promise compatibility after 2099. Enforce calendar validity and chronology separately. If the owner rejects the century interpretation, identity/schema adoption waits for an alternative parser contract rather than guessing historical dates.

## Commands and error contract

Package name ft3_tools; commands run from an installed package or repository root via python3 -m ft3_tools.

- audit --catalog-root DIR --profile legacy|uuid --format json|text: reads filesystem inputs; reports every safe-to-discover violation; existing defects fail strict audit.
- check-change --repo DIR --base SHA --head SHA --format json|text: resolves inputs once; reads catalogs at head and contracts, profiles, exception policy and identity registry at base. Base must be an explicit full commit SHA. Git data is accessed as inert blobs. No candidate manifest/anchor/transition override.
- export --catalog techniques|tactics --catalog-root DIR --profile legacy|uuid --output FILE [--check|--replace]: one CSV output per invocation. Check mode is read-only. Normal export atomically refuses existing output unless replace is explicit, including destinations created after staging. Refuse input overlap and symlink destinations. Load only the selected JSON source and contract; missing/malformed existing CSV or an unrelated catalog cannot prevent projection. Validate export-relevant JSON structure/identity before writing; relationships/dates remain visible in audit and are not silently repaired by export.
- changes --repo DIR --base SHA --head SHA --format json|markdown: shows technique and tactic additions/removals, exact field changes, identity changes, order/header changes, and diagnostic deltas. Duplicate or invalid identity prevents complete matching: return exit 2/completed:false with safe partial results and ambiguity diagnostics; never infer additions/removals for ambiguous records. Valid uniquely matched data with policy violations produces a complete exit-1 report.

Exit 0: complete requested run and policy passed. Exit 1: complete run with data/policy violation or export mismatch. Exit 2: invocation, decoding, filesystem, Git, trust, ambiguous change matching or unexpected operational failure prevented completion. audit/check-change return exit 1 for decoded invalid head data after completing safe diagnostics; changes has the explicit incomplete-matching exception above. Malformed JSON/CSV/UTF-8 are exit 2. Dependent checks skip unsafe records but retain their schema diagnostic. JSON stdout is a single versioned report; operational explanation goes to stderr. Operational failure still yields completed:false/passed:false when JSON output was requested, including invalid invocation where format can be recognized.

Reports identify tool version/digest, contracts/policy digests, catalog digests, resolved commits, completed/passed/catalog_clean, counts and stable diagnostics. Diagnostics use structured expected/actual fields and canonical fingerprints; no Python repr strings or wall-clock timestamps in deterministic payloads. Reports are not a trust root: the trusted runner supplies the accepted base.

Trusted resource defaults: 4 MiB per blob, 16 MiB total catalog bytes per snapshot, 10,000 technique/1,000 tactic records, 256 KiB per field, nesting depth 64, 10,000 diagnostics and 32 MiB serialized report. These are versioned operational bounds with substantial headroom over current ~1 MiB catalogs, not frozen catalog counts. Limit breach returns 2/completed:false with a limit diagnostic, never a truncated passing result. Read bound bytes before parsing; bound JSON nesting before object construction, set CSV field limits, validate record/field sizes, and stop diagnostic accumulation at the bound. Each Git subprocess has a 30-second timeout and each full CLI run a 120-second supervised timeout with child cleanup. Trusted hosted runner additionally enforces a 1 GiB Linux process/container memory budget; local macOS tests exercise input bounds and deadlines without claiming a hostile-data memory sandbox. Adjusting limits requires trusted policy adoption.

All text/log display escapes ANSI and control characters; JSON retains exact data through JSON escaping. Text and Markdown outputs never emit raw workflow-command prefixes from candidate strings. CI stores structured report data as an artifact and logs only trusted summaries, not raw field contents. Test ANSI, carriage returns, Unicode controls and ::warning::/::set-output:: strings. Escaping is presentation-only; input values/fingerprints remain unchanged.

## Trusted policy and identity

check-change cannot prove that a caller-chosen SHA is trusted; the protected runner or human reviewer selects the accepted base externally. It must reject abbreviated/moving refs and must never replace missing history with working-tree files. Candidate contract/policy/bootstrap changes are adoption-required, not silently consumed. The only candidate registry mutation allowed without prior adoption is the narrow mechanically checked addition delta: existing base entries remain identical and present; new entries equal exactly newly added valid catalog ID/UUID pairs. Missing, extra/unrelated, reused or changed retained entries fail. This cannot amend trusted assignments or historical entries.

Known-defect exceptions are exact fingerprints from a strict audit of the actual selected baseline, with affected fields/values, rationale, owner and next action. Fingerprints include catalog, stable identity, rule, field and canonical expected/actual values; row positions are display-only and excluded, so reordering does not revoke an unchanged exception. They apply only when the same diagnostic exists in base and head. New/worsened/reintroduced defects fail. Resolved exceptions are reported; stale entries cannot suppress a different defect. A correction promised by the contribution must disappear; merely labeling it fix_in_pr does not count. Candidate policy additions cannot excuse their own catalog change. Removing resolved exceptions is a cleanup change; adding exemptions or changing contracts requires prior trusted-policy adoption.

Before UUID adoption preserve FT IDs in both catalogs. After adoption compare every current UUID to base assignments and an append-only identity registry retaining all adopted identities. New records require fresh UUIDv4s never present in active or retained history. Ordinary title/prose/tactic/order changes preserve identity. Policy/registry changes that bless old reassignment or edit retained entries fail. Additions extend the registry with exactly the new catalog pairs; existing entries are logically identical, with formatting-only changes reported separately.

Bootstrap binds two distinct things: immutable assignment provenance at ee763e93da9a8868db583987aa1b77faa7331c40, and trusted bootstrap baseline fingerprints of the exact accepted legacy catalog. The former remains historical evidence; the latter enforces a pure UUID-only catalog transition. The accepted base must already contain reviewed assignment values, selected baseline SHA and complete canonical non-UUID fingerprints; candidate rows stripped of UUID must equal the actual base rows and that frozen input. Candidate cannot supply or refresh those fingerprints. Preserve all 137 prepared UUID values.

Executable rollout: first prepare/adopt trusted tools and bootstrap policy against the selected accepted legacy baseline; next compare a pure UUID candidate; then compare later parent/content corrections using the adopted UUID baseline. Existing 2838d3eceb57e384de8c96dfd93638577754d34f is the UUID-stage catalog corresponding to ee763e93; combined 4e5a4b5 contains 31 later parent edits and is not a pure bootstrap. If those parent edits land before UUID adoption, independently review and adopt refreshed bootstrap-baseline fingerprints at that accepted legacy revision while retaining assignment values/provenance. Until then the changed-input bootstrap fails; a candidate-written refresh never authorizes it.

Protected adoption is a separate two-stage process, avoiding required-check deadlock. A contract/policy/bootstrap/accepted-tool change first contains zero production catalog-byte changes and produces an expected non-passing adoption-required receipt. Named authorized maintainers independently approve its exact base/head/digests; if a required check blocks it, they use a recorded narrowly scoped one-time protection bypass or separately protected policy-pin update. That operation is outside this local implementation and requires explicit user/maintainer authorization. Update the accepted runner/tool/policy pin only after the reviewed adoption revision is accepted; the later catalog contribution refers to that earlier revision and cannot combine catalog changes with adoption. Tests reject mixed adoption+catalog changes and unapproved runner-pin updates. The valid new-record registry append defined above is not policy adoption.

## Export compatibility

JSON is proposed as the canonical projection source; adoption is separate from writing the exporter. Technique parity prerequisite and all 12 tactic domain conflicts must be decided before any generated CSV replaces production CSV. No override map hides the tactic disagreement. Export check currently reports existing mismatches honestly.

Output: UTF-8 without BOM, explicit contract column order, JSON array row order, comma delimiter, double-quote quoting with doubled escapes and minimal quoting, CRLF record boundaries, no final record terminator (matching current files), and unchanged embedded newline characters/string whitespace. Validate byte expectations against frozen excerpts before locking this convention. Export must round-trip every field exactly and produce identical bytes on repeated runs. Formatting differences are reported, not automatically applied.

Export builds and validates complete bytes before publication and stages a temporary sibling file. On supported POSIX platforms normal mode atomically links the staged file to the destination with no replacement, failing if any destination already exists, then removes the staging name. Explicit --replace alone uses atomic replacement after safety checks. Resolve the parent once and use directory-relative operations to avoid mixing destinations during the run. Tests inject concurrently created regular files and symlinks between staging and publication. Preserve external/previous destination bytes on every pre-publication failure, clean temporary files, and distinguish publication completed from durability failure. Do not claim atomicity across two output files or a hostile-filesystem security sandbox. Never export to tracked catalog locations during the infrastructure cut.

## CI and adoption

The candidate test workflow uses read-only permissions, pinned actions, no secrets, no persisted credentials or publication rights. It runs lint, the full suite and portable clone/export/consumer scenarios. Candidate-code CI verifies correctness; it is not a hostile-PR authorization boundary.

The enforcing comparison must execute tool code/contracts/policy from an independently selected protected revision, while reading candidate catalogs as inert data. Initial infrastructure adoption cannot certify itself: local full-run evidence and independent human/model review are its bootstrap gate. Deliver a documented trusted-runner procedure; activate an enforcing hosted check only after a maintainer verifies its protected code source, head-SHA binding, required-check behavior and fork behavior. Production readiness is reported separately from hosted enforcement activated; no security guarantee is inferred from a candidate-modifiable workflow.

Hosted activation must also prove a candidate workflow emitting the same check/job name cannot satisfy the gate: protection binds the expected independently trusted check source/app/workflow, not just a string name. Test fork PRs, head update/rebase, stale receipts, synthetic merge commits and merge queues if enabled. Every accepted check binds to the exact commit the merge policy evaluates. If the platform cannot demonstrate these protections, hosted enforcement remains pending; do not weaken required checks or claim activation. No GitHub settings/App installation/write is part of local implementation.

Git reads use argument arrays, fixed inert blob paths, no shell or textconv, and full SHA resolution exactly once. Scrub inherited GIT_* settings, disable system/global config, replacement objects, hooks, fsmonitor, optional writes and prompting, and refuse promisor/partial-clone or alternate-object dependencies in the comparison object store. The trusted runner creates its own ordinary bare object store and fetches explicitly pinned inputs during setup; it does not read candidate checkout config. No lazy fetch occurs during validation. Test hostile environment/local config/replace refs, missing objects, timeouts and child cleanup. Trusted Python runs the verified installed tool with -I outside candidate cwd to prevent import injection.

Supported runtime targets: Python 3.11, 3.12, 3.13 and 3.14 on Linux; macOS smoke/atomic-filesystem tests on 3.14. No Windows support claim. Runtime and tests use standard library; lint tooling is an exact hash-pinned development dependency selected and recorded in Task 1. Fixtures are tracked excerpts/synthetic data and temporary git init repositories, not shared clones or workstation object databases. No network is required for tests after development dependencies are installed.

Durable receipts are generated by tests/record_runs.py into artifacts/ft3-infra/<scenario>/receipt.json with stdout/stderr/report files and SHA256 digests. receipt.schema.json defines schema_version:1, scenario, exact argv, exit/completed/passed, expected outcome, tool/base/head/policy/contract/catalog/lock digests, output digests and environment metadata (OS/runner image identity, Python/Git versions and pinned action SHAs when hosted). Separate environment metadata from deterministic command payloads; clean-clone regeneration compares payload bytes/digests and scenario outcomes, while recording legitimate environment differences. Raw artifacts are ignored in Git; a concise final local acceptance manifest records their paths/digests and is reviewable. Hosted artifacts use 30-day retention and must be downloaded/preserved with the local handoff before expiry.

## Acceptance and limits

All scenarios in the companion edge-case matrix must have named tests and expected exits. Full runs must work in a fresh clone and a depth-1 file:// clone. Missing requested baseline objects fail clearly; explicit fetching is a runner prerequisite, not a validator fallback. All checks/reports prove no mutation by before/after hashes and Git status. All consumers retain FT-code lookup, optional adopted UUID lookup, wire types, headers and values; duplicate titles remain distinct.

Strict audit of original upstream intentionally fails on its known defects; the combined candidate intentionally reports its 25 remaining diagnostics. Comparison can pass only with precise trusted baseline allowances. No claim of catalog content correctness, real-world detection efficacy, live MISP import/attachment retention, STIX compliance or maintainer acceptance comes from these gates.

The final implementation must have complete reproducible receipts for exact base/head/tool/policy inputs, passing regression and consumer runs, and no unresolved Critical/Important implementation-review finding. Upstream publication remains a separate user decision.
